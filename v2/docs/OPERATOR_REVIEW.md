# Operator review — controlled foundation

Disabled by default (`ENABLE_OPERATOR_REVIEW=false`). Apply migrations through **0031**, explicitly provision separate review database service roles, configure `OPERATOR_DATABASE_URL`, and rebuild API/web before enabling. See [review export and database-role setup](REVIEWED_EXPORTS.md). Private support and reviewed exports are separately disabled (`ENABLE_OPERATOR_PRIVATE_REVIEW=false`, `ENABLE_REVIEWED_EXPORTS=false`); dashboard activation alone does not activate these routes. No live operators were provisioned during implementation.

Bootstrap: an authorized database administrator must explicitly insert the first verified identity issuer/subject into `platform_operators`, with role ADMIN and active=true. Use parameterized SQL and the administrator's audited change-management tooling; email and candidate membership are not authority. There is no unauthenticated bootstrap route.

After bootstrap, an active ADMIN with recent MFA can provision, change or revoke a different operator through `POST /v1/operator/roles`. REVIEWER accounts and self-targeted commands are rejected. Changes are transactional with an append-only audit entry and immutable replay receipt. Replaying a successful old grant returns its original acknowledgement; it does not re-grant access after a later revocation. Current caller authorization is rechecked before every replay.

The Node-pinned CLI is `npm run operator:provision -- command.json`. Supply `OPERATOR_API_ORIGIN` and `OPERATOR_ACCESS_TOKEN` through a protected process environment, never command arguments or the JSON file. Only HTTPS or loopback HTTP origins are accepted; redirects are rejected. JSON contains `requestId` (UUID), `issuer` (exact verified issuer URL), `subject` (exact verified subject), `role` (REVIEWER or ADMIN), and `active` (boolean). Keep requestId and payload unchanged for a retry; use a fresh UUID for a new command. The CLI does not print tokens or response payloads. The initial bootstrap and disaster-recovery DB actions remain outside this API's audit channel.

The dedicated OIDC verifier uses configured OIDC issuer/audience/JWKS, RS256/ES256, expiry, exact subject, `amr` containing `mfa`, and `auth_time` within 15 minutes. Provider-specific MFA claim adapters are not implemented; providers lacking these claims fail closed. A normal development token cannot access this feature. The browser uses the existing signed-in token and cannot manufacture claims. Step-up must occur at the identity provider; in-app step-up UX remains pending.

Open `#operator` after sign-in. The default case list groups value-free failures by release/stage/code and shows distinct reported application-run counts. It exposes no candidate IDs, answers, notes or documents. When separately enabled, the support panel can request access to one candidate-selected note under the consent protocol below. OPEN/INVESTIGATING/RESOLVED/DISMISSED are triage statuses only, not proof of a repair or authority to publish a rule.

Cases now expose revision-safe review metadata: responsible layer, expected behavior and one allowlisted synthetic-suite reference. Detail includes the latest 100 case-change audit entries. References are categorization aids, not proof of a reproduced defect or passing evaluation. No free-form URLs, executable attachments or private candidate evidence are accepted.

Packaged references: ADAPTIVE_AUTOFILL → `npm run test:adaptive-autofill`; PRIVATE_NOTE → `scripts/private-note-browser.ts`; LEARNING_RECOVERY → `scripts/learning-recovery-browser.ts`; OPERATOR_REVIEW → `scripts/operator-review-browser.ts`. Run the latter scripts with `bash scripts/with-node.sh node --import tsx <path>`. These are synthetic tests; attaching a reference never runs it or authorizes a release.

Every successful repository access and authenticated role denial is audited. Case changes carry expected revision and UUID request identity. Replay returns the original result; conflicting edits and request-ID reuse across action types reject. Audit and new receipt rows reject update/delete. Invalid JWTs and malformed payloads are rejected before repository execution, not inserted as claimed subjects into this table. Failed repository actions write a separate ACTION_FAILED record after rollback, without error payloads. These failure records currently identify the actor/time, not the case or detailed rejection category; database outages can also prevent audit persistence. Do not treat this as a complete request-failure log.

Cases support self-claim, self-release and explicit ADMIN_RELEASE. Only open/investigating, unassigned cases can be claimed. Another reviewer cannot steal/release a claim; an active administrator can release abandoned assignments. Every change checks expected revision and uses existing immutable receipts/audit. Replay does not reapply a released claim; current role access is always checked. Assignment coordinates work, not permissions: other authorized operators can still triage/edit the case, but receive no private-note authority from assignment.

## Scoped private support (checkpoint 11)

Both operator flags must be true, with configured OIDC, active provisioned operator, candidate sessions and the existing note encryption key. The candidate uses Attention → a saved note → **Share this note with support**. The operator uses `#operator` → case → **Candidate-approved private review**. Full behavior and limits: [support consent implementation](SUPPORT_REVIEW.md).

Checkpoint 12 adds explicit revision-safe case merging, preserved member evidence/unique run counts, and optional immutable strategy proposals → trusted evaluator → independent approval → compatible export/disable/rollback. Root views preserve access to original member artifacts and the original requester's grants. This is export selection, not runtime activation. Separate runtime/evaluator database roles and actual consent/read/revoke plus a lock-expiry race passed in disposable PostgreSQL. Full setup, invariants and tested boundaries: [reviewed exports](REVIEWED_EXPORTS.md).

Limitations: group materialization happens on operator list and is limited to 100 categories. Retention, anomaly alerts, detailed failure correlation and complete operational metrics are not implemented. Private support shares one existing encrypted note, not a general diagnostic-package export or profile browser. Review database roles are trusted service roles; per-person and consent checks remain in the repository/API. In-app MFA step-up, broader synthetic reproduction artifacts and runtime deployment integration remain open. Do not describe this as the complete AF-07/08 system or production security certification.
