# Reviewed strategy exports — checkpoint 12

This is a controlled **export-only** workflow for existing registered Q strategy definitions. It does not hot-load a strategy, approve Q deployment, start a canary, rewrite an issued plan or submit an application. All three operator feature flags remain off by default. No live database, credentials, operator identities or installed extension were changed during implementation.

## Deployment prerequisites

1. Apply the normal ordered migrations through **0031** using the migration owner, and rebuild API/web under the pinned Node runtime. Do not use a service login to migrate.
2. An authorized DBA explicitly runs `database/security/review-service-roles.sql` in that database. This is deliberately outside startup and the migration runner. It creates two NOLOGIN permission groups, not users/passwords: `job_hunter_review_runtime` and `job_hunter_review_evaluator`. The file is transactional and repeatable.
3. Provision **two different login roles** in secret-managed DBA tooling. Neither may own tables/schema, create roles/databases, bypass RLS, be superuser, or belong to a privileged/other review group. Grant each login only its respective permission group, with inherited permissions; never grant both groups to one login. Use TLS for remote databases. Do not put credentials in a command line, checked-in file or support message.
4. Configure `OPERATOR_DATABASE_URL` for the runtime login. Candidate services still use `DATABASE_URL`. Enabling operator review without the dedicated connection and complete OIDC settings rejects startup. Startup checks reject the owner, unsafe memberships, broad profile/document reads and crossed evaluator/runtime permissions. These checks supplement—not replace—a DBA grant/security audit.
5. Configure `REVIEW_EVALUATOR_DATABASE_URL` **only in the trusted local/CI evaluator environment**. It must not be deployed to the API process. It needs no candidate encryption key or live Q signing key. The worker never falls back to `DATABASE_URL`. Existing npm tooling can load a protected local `.env`; production must use process-specific secrets.
6. Bootstrap a verified first operator through the audited DBA process in [operator setup](OPERATOR_REVIEW.md). Enable `ENABLE_OPERATOR_REVIEW=true` and, separately, `ENABLE_REVIEWED_EXPORTS=true`. Private notes additionally require `ENABLE_OPERATOR_PRIVATE_REVIEW=true`. Normal candidate/development tokens do not authorize operators.

The permission groups are trusted **service roles**, not direct browser or human SQL accounts. The runtime can read encrypted note columns and ownership metadata to perform exact-note support consent checks, but not normalized profile values or résumé documents. Actual consent, operator identity and decryption are repository/API responsibilities. Candidate-data locks have UPDATE(id) permission but a restrictive WITH CHECK(false) policy rejects actual writes, even with forged tenant settings. The evaluator cannot read notes/profile/documents or write approvals/exports; the runtime cannot insert evaluation results. The migration owner and the broader candidate API remain trusted; this is not process isolation against a compromised API with its main database credentials.

## Workflow and invariants

- From an open/root case, load **Reviewed strategy exports**, select a registered version, and propose it. No arbitrary JavaScript, matcher or caller-supplied execution plan is accepted. The immutable artifact binds the exact definition hash, original case and API/extension protocol 1.
- A trusted maintainer runs `npm run review:evaluate -- <artifact UUID>`. This command uses the separate evaluator login and actual packaged browser executor/verifier in fresh synthetic Chromium. The current supported corpus is native text/textarea only, with 16 scenarios including React commitment, reversion, disabled targets, user intervention, dynamic fields, ownership, declarations, duplicate execution, fallback and expiry. Unsupported capabilities fail closed.
- The worker hashes owned package sources **and compiled package files**, extension sources, evaluator/fixture scripts and lockfile before/after evaluation. An edit during evaluation invalidates the run. A runner exception or malformed result records a failed evaluation, not a pass. This is reproducible local evidence, not a sealed holdout or signed full-release artifact.
- There is no HTTP evaluation/proof-upload endpoint. Browser status, model confidence and an operator-provided `passed: true` cannot count as proof. The evaluator's restricted SQL identity is the result-writing authority; people with that credential remain trusted. Future isolated CI attestation/holdout protection is not implemented here.
- A **different active ADMIN** must explicitly approve the exact immutable hash and its newest passing evaluation. Results expire after seven days. A newer result, including a failure, supersedes old approval. A different artifact cannot reuse approval. Expiry and role status are checked again at export/read/rollback; wall-clock expiry is rechecked after blocking authority locks.
- Preparing an export checks the global expected revision and appends an immutable export record. The response and UI say **EXPORT_ONLY_NOT_DEPLOYED**. A manifest read rechecks authorization, exact hashes, current passing result, active approver and both protocol numbers.
- Disable blocks future manifest reads after commit. It cannot recall a manifest someone already read. Rollback selects the **original previous export ID**, only if still eligible; it does not clone a release, rewind history, edit truth or replay browser actions. Retrying an old successful prepare after disable returns its original receipt without reactivating it.
- Proposals, evaluations, approvals and export records reject update/delete. Operations use existing actor/request-ID receipts and append-only audit. Audits contain reference IDs/hashes, not plans, private answers or error excerpts. Failed actions retain the existing limited actor/time failure audit.

## Merge behavior

Merging requires explicit confirmation, current revisions for both cases and an open/investigating root target. Roots/children are flattened under the target; cycles, self-merges and more than 100 total evidence groups reject. Counts deduplicate application runs across all member groups. Original case IDs, audit history, artifact hashes and private grants are preserved. Root views include member artifacts and the caller's original grants. Grants never transfer to a target's assignee or another administrator. Historical sources remain readable but cannot be edited/assigned/remerged; new support/proposal requests use the root. No automatic unmerge exists.

## Verification commands and honest limits

- `npm test`: production repository/API/contract tests, with isolated PGlite for fast database cases.
- `npm run test:review:browser`: production React components against a synthetic API; explicit merge and approval confirmation, evaluation gates, export status, inert manifest and denial clearing.
- `npm run test:review:postgres`: requires Docker plus an already-installed `postgres:17-alpine` image. Creates a random labelled loopback-only container with tmpfs data, runs migrations and actual restricted-login repositories, launches the real positive/negative browser evaluator, then removes only that container. Never reads the project's `DATABASE_URL`, creates persistent volumes, auto-downloads software or submits applications.

The PostgreSQL test certifies these review-service permissions and one two-connection consent-expiry race, not every candidate API policy or all transaction crash points. Current evaluator supports only text strategies; canonical aliases, semantic/context defaults, entity matching, broad representations, locked holdouts, fully packaged release signatures, stable runtime cohorts and governed deployment integration remain later work. Existing stronger Q rollout gates still apply. Neither triage status nor reviewed export implies measured live autofill accuracy.
