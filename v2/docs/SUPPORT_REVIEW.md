# Scoped support review — checkpoint 11

Implemented as an opt-in diagnostic flow, not automatic learning or access to candidate profiles. Source: `packages/database/src/support-review.ts`, `apps/api/src/support-routes.ts`, `apps/web/src/SupportReview.tsx`; migration `0029_support_review.sql`.

## Activation and rollback

No live migration, operator provisioning, candidate data changes or employer submissions were performed. Apply the existing ordered migration command through 0031, follow the [separate review service-role setup](REVIEWED_EXPORTS.md), configure `OPERATOR_DATABASE_URL`, rebuild/restart API and web, and deliberately enable **both** `ENABLE_OPERATOR_REVIEW` and `ENABLE_OPERATOR_PRIVATE_REVIEW`. Both default to false. OIDC issuer/audience/JWKS, active provisioned issuer/subject, recent MFA, candidate sessions and the existing private-note encryption key remain mandatory. Never paste secrets into logs or support requests.

Disabling the private flag and restarting removes all support routes while preserving ordinary operator triage. It does not delete audits or revoke grant rows: grants continue expiring naturally, so re-enabling before expiry can restore still-valid consent. Candidates cannot revoke through absent routes; to invalidate consent permanently before a temporary disable, revoke the relevant grants first. Downgrading code does not require destructive migration rollback. No default administrator or self-promotion route is introduced.

## User flow

1. An active operator with recent MFA chooses a case and one purpose: debugging autofill, representation or learning. The request is valid for 24 hours and provides an opaque UUID. Retries with the same caller/request UUID return the original request; changed case/purpose conflicts.
2. Share that code through an existing trusted support channel. The application does **not** message the candidate or grant access automatically.
3. In Attention, the candidate chooses one existing private note and enters the code. Preview displays the exact requesting issuer/subject, case and purpose. The note's owning application run must have a recorded failure matching that case's release/stage/code. This is run-level relevance, not proof that this exact question caused the failure.
4. The candidate reviews the question/answer already shown above, chooses 15 or 60 minutes and explicitly checks consent. Only then can approval be sent. The server binds consent to that account, candidate, note and requesting operator. No profile/resume/employment history is copied into a support package.
5. The operator refreshes request metadata and explicitly clicks **View approved note**. Listing never fetches private text. Each read is a POST with no-store response, reauthenticated with recent MFA and an active operator record; only the original requester can read, even if someone else is an administrator or owns the case assignment.
6. The candidate can list and revoke grants for the note, including after deleting the note. Replay never extends approval or reopens revoked access. Private note deletion/expiry, candidate/account inactivity, operator deactivation, grant expiry and revocation independently block subsequent reads.

## Guarantees and bounds

- No private payload in grant rows, support audit or case metadata. Reads decrypt the existing note only after authorization and use an allowlisted question/answer response. Parser/decryption failures become a fixed error, without private excerpts in request logs.
- Expiry is the earlier of the chosen duration and note expiry. Approval rechecks wall-clock expiry after waits; reads recheck after acquiring locks. Shared note/account/operator locks and exclusive grant locks coordinate with revocation/deletion/role changes. PGlite covers the broad matrix; checkpoint 12 additionally verifies actual restricted-login repositories and a two-connection note-lock/expiry race in disposable PostgreSQL. This does not certify every possible lock interleaving.
- Candidate ownership comes from the authenticated session, never body parameters. Operator authority comes from verified issuer/subject plus the active DB role, never browser role/email. All support body schemas are strict and bounded.
- At most 20 live requests per operator/case, and 20 live grants per note. A bounded recent list returns at most 100 operator requests or 200 candidate grants, with live entries first; this is not complete historical pagination. Expired/revoked rows remain as metadata. Reuse original request IDs when uncertain whether creation succeeded.
- Each successful request, preview, approval, listing, revocation and private read has an append-only support audit. Failed repository work writes a separate value-free DENIED record after rollback. Audit failure prevents returning private text. Invalid JWTs/schema failures occur before repository access, and database outages can prevent denial persistence; this is not a complete HTTP failure log. Denials intentionally do not record an unverified grant ID or raw error.
- The browser renders question/answer as inert React text. Private text clears after at most 30 seconds, at consent expiry according to the browser clock, on focus/visibility loss, panel close or access failure. Late replies after hide/unmount/context change are ignored. Server expiry remains authoritative; client timers are an exposure-reduction aid, not a security boundary.
- Revocation blocks future authorized reads; it cannot erase information already observed, screenshots, browser developer-tool responses or copies made by the recipient. No claim of DRM or retroactive recall.
- Viewing a note does not confirm a reusable answer, train a model, publish a strategy, modify candidate truth or submit an application. Existing candidate note → explicit global confirmation remains a separate workflow.
